# 端侧与服务器端的 KV 置换粒度：研究思考与实验假设

## 1. 核心观点

前缀切分和 KV 置换不是同一个问题：

- **前缀切分**决定一条请求被拆成多少个可复用节点；
- **KV 置换**决定缓存空间不足时淘汰哪些节点、LoRA 分支或完整会话。

因此，端侧并不是“完全不需要前缀切分”，而是更可能采用**粗粒度切分 + 会话/LoRA 组级淘汰**；服务器端则更适合采用**细粒度前缀树 + 祖先保护 + 叶子优先淘汰**。

## 2. 为什么端侧和服务器端不同

### 2.1 端侧工作负载

端侧通常只有一个用户，GPU/内存预算小，LoRA 切换可能比较频繁，但同一条历史会话的回访次数有限。此时保留很多细粒度叶子节点会带来：

- 节点元数据和哈希查找开销；
- 多个 LoRA variant 占用显存；
- 跨 LoRA delta 构建和校验成本；
- 低概率回访时的无效驻留。

所以端侧可以把下面的对象作为一个置换单元：

```text
conversation_id × lora_id × prefix family
```

当该组的预计回访收益低于恢复成本时，整体释放，而不是只淘汰其中一个叶子。全局 system prompt 或极短的共享模板仍可以固定保留，因为它们的复用概率通常更高、占用也更小。

### 2.2 服务器端工作负载

服务器可能同时处理大量用户和大量 LoRA。不同请求往往共享系统模板、工作流说明或任务格式，因此靠近根部的节点可能被许多请求共享；用户个人信息、日期、站点和历史对话则通常在较深位置分叉。

服务器端更适合：

1. 固定或优先保留高扇出的祖先节点；
2. 根据未来复用概率、共享用户数和内存成本淘汰低价值叶子或子树；
3. 对 LoRA variant 单独计算热度，不因为某个热门祖先就永久保留所有 variant。

但“很多人都在订火车票”不等于“叶子节点一定可以复用”。只有字节级前缀相同才能直接命中；不同出发地、日期和车次通常只共享较浅的系统/流程前缀，语义相似本身不能产生 exact KV 命中。

## 3. 火车票场景的具体解释

一个连续请求可以写成：

```text
R1 = S + C + T_search       (LoRA 1：查询车票)
R2 = S + C + T_book         (LoRA 2：提交订单)
R3 = S + C + T_alarm        (LoRA 3：设置提醒)
```

其中 `S` 是系统提示，`C` 是用户和当前会话上下文，`T_*` 是不同任务的指令。

### 3.1 端侧的预期行为

如果 `R1 -> R2 -> R3` 只发生一次，且之后很少回到该订票会话：

- `S` 可以保留；
- `C` 和对应 LoRA variant 的 KV 作为一个会话组管理；
- LoRA 1、2、3 之间不应默认生成可复用 delta；
- 组的回访概率低、恢复成本高时，整体淘汰 `conversation_id` 对应的 KV family。

这里的关键不是“LoRA 不同所以一定不能复用”，而是要测量跨 LoRA delta 的有效概率：

```text
q_delta = 可通过质量校验的 delta 分支数 / 尝试构建的 delta 分支数
```

如果 `q_delta` 很低，继续保存 delta 只会增加端侧的显存、计算和校验开销。

### 3.2 服务器端的预期行为

如果大量用户都使用同一订票流程，则可能出现：

```text
root -> shared booking system prompt -> station/date template -> user-specific details
```

此时共享 system prompt 和订票流程模板具有较高扇出，应优先保留；具体用户的日期、车次和历史位于叶子或深层子树，按热度和容量淘汰更合理。

## 4. 建议的置换策略

### 4.1 端侧：组级收益策略

对会话/LoRA 组 `g` 定义：

```text
value_edge(g)
  = P_return(g) * reusable_tokens(g) * time_saved_per_token
    - memory_bytes(g) * memory_cost
    - restore_cost(g)
    - delta_cost(g)
```

当 `value_edge(g)` 低于阈值时，整体淘汰该组；组内不再单独优化叶子顺序。只有全局共享的短 system prefix 可以使用更高的保留优先级。

端侧推荐配置：

```text
切分：128~256 token 的粗粒度，保留会话/LoRA 边界
置换：conversation × LoRA family 原子淘汰
delta：只有 q_delta 和回访概率同时足够高时才构建
```

### 4.2 服务器端：节点价值策略

对前缀树节点 `n` 定义：

```text
value_server(n)
  = shared_users(n) * P_reuse(n) * reusable_tokens(n)
    / (memory_bytes(n) + epsilon)
```

高 `shared_users`、高回访概率且位于根部的节点优先保留；低热度叶子和低价值 LoRA variant 优先淘汰。淘汰时需要检查祖先依赖，不能释放仍被子节点引用的节点；更适合释放完整低价值子树或某个 LoRA variant 分支。

## 5. 对“修改量化模型权重”的修正

不建议通过重新量化或修改模型权重来隐式表达缓存淘汰偏好。量化主要影响模型精度、显存占用和计算速度，不直接提供可靠的缓存热度信号。

更合理的做法是：

- 在运行时显式维护会话回访率、LoRA 切换率、delta 质量和恢复成本；
- 使用轻量级的离线/在线预测器估计 `P_return` 和 `q_delta`；
- 将预测结果输入 KV cache 的置换评分，而不是改变语言模型本身的权重。

## 6. 可以向导师汇报的正式表述

> 端侧和服务器端不应采用相同的 KV 置换粒度。端侧通常面向单用户和有限显存，跨 LoRA 的连续任务虽然共享文本上下文，但由于 LoRA 变换不同，delta 可复用概率可能较低；当某个会话在短时间内不会再次访问时，继续保留其细粒度叶子节点的收益不足以抵消显存、调度和恢复开销。因此端侧更适合保留全局共享 system prefix，并以 `conversation × LoRA` 为单位进行粗粒度切分和组级淘汰。服务器端具有更高的并发度，不同用户可能共享相同的系统提示和任务模板，靠近根部的前缀节点具有更高扇出和更高复用价值，因此更适合采用前缀树结构、优先保护热门祖先、从低热度叶子或 LoRA variant 分支开始淘汰。需要注意的是，多用户执行相同任务不等于完整前缀可复用，只有字节级共享前缀才能直接命中；最终策略应由回访概率、共享用户数、delta 质量、节点内存和恢复成本共同决定。

## 7. 建议的对比实验

| 实验维度 | 端侧组级策略 | 服务器节点级策略 |
|---|---|---|
| 请求规模 | 单用户、1~4 个会话、LoRA 频繁切换 | 多用户、多个共享任务模板 |
| 置换单位 | `conversation × LoRA family` | 前缀树叶子、子树、LoRA variant |
| 主要变量 | 会话回访率、LoRA 切换率、`q_delta` | 共享用户数、祖先扇出、prefix 热度 |
| 主要指标 | TTFT、显存峰值、组恢复次数、delta 构建次数 | TTFT、token 命中率、节点淘汰率、跨用户复用率 |
| 主要假设 | 低回访时组级淘汰优于叶子淘汰 | 高扇出祖先保护优于全局 LRU |
