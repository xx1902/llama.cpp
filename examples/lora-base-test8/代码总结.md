# LoRA Prefix-KV 实验代码综合总结（test8）

## 1. 文档目的

这份文档把 `lora-base`、`lora-base-test` 到 `lora-base-test7` 的代码和实验脚本按演进顺序串起来，说明每个版本解决的问题、增加的代码、仍然存在的限制，并给出一次请求在系统中的完整路径。

`test8` 选择 `lora-base-test4.cpp` 作为综合实现。原因是 test4 同时包含：

- 完整 prefill/decode baseline；
- 同 LoRA 精确 prefix KV 命中；
- 跨 LoRA anchor + Q8 delta 探测、构建和质量校验；
- 分块 Prefix Tree；
- GPU full、Host full、Host delta 三级驻留；
- family 评分、降级和淘汰；
- file/service/oracle 预测预取；
- CPU、CUDA 同步和 CUDA 重叠 delta 执行。

test8 主要增加中文阅读注释和独立构建目标，不改变 test4 的算法语义。这样既保留可复现实验，又避免把后续 test5 的专项计时逻辑误当成通用缓存运行时。

## 3. 各版本逐一说明

### 3.1 `lora-base`：生成式 LoRA 树和共享前缀原型

`build_lora_tree.py` 先把 LoRA 组织成 group tree，每个 group 选择一个 anchor LoRA，并保存若干叶子 LoRA 和 prompt 模板。`lora-base.cpp` 启动后完成以下工作：

1. 加载基础模型和生成的树结构；
2. 把静态节点转换为运行时结构并加载 adapter；
3. 对 prompt tokenize，并按 token 前缀相似度选择 group；
4. 为 group 的共享 prefix 做一次 prefill；
5. 通过 `llama_memory_seq_cp` 把 prefix KV 复制到请求序列；
6. 绑定 anchor -> child 的 LoRA 路径，计算 suffix 并 decode。

这个版本证明了“共享文本 prefix 可以减少重复 prefill”的可行性，但 group 路由是离线静态的，缓存容量、跨 LoRA delta、请求到达顺序和失败回退都还不完整。

### 3.2 `lora-base-test`：第一次把 delta 和在线回放放在一起

这一版把实验拆成两个独立部分：

- 离线部分比较不同 LoRA 在相同 token prefix 上生成的 K/V，计算 cosine、L2，并尝试构建 Q8 anchor + delta；
- 在线部分按 `grouped_requests.jsonl` 到达顺序回放，只在 prefix token 和 LoRA 都完全相同时命中缓存。

新增的 `online_prefix_node`、`online_route_result`、`sample_result` 和 `kv_delta_probe_*` 结构，使代码可以同时记录命中长度、suffix 长度、delta 质量、显存和 TTFT。它明确禁止语义相似或“相似词”复用，避免把文本相似误写成 KV 等价。

主要问题是：配置写死较多，数据结构与 JSON workload 脱节，在线缓存基本是整段 prefix，跨 LoRA delta 仍以实验性 probe 为主。

### 3.3 `lora-base-test2`：系统化的 Prefix-KV 运行时

test2 解决了 test 的可复现性和系统管理问题，增加：

- `experiment_options`：统一模型、上下文、缓存上限、delta、预取和 family 权重；
- `load_lora_config`、`load_requests`、`load_delta_pairs`：从 JSON/JSONL 载入真实 workload；
- `tokenized_request`：严格验证 `common_prefix_text` 是完整 prompt 的 token 前缀；
- chunked Prefix Tree：同一个节点可以保存多个 LoRA variant；
- `cross_lora_policy=off|sync|deferred`：控制请求路径是否构建跨 LoRA delta；
- Host full、Host delta 和 GPU full 三种驻留状态；
- delta store：把 Q8 delta 保存/加载到磁盘；
- family 价值评分：综合频率、预测概率、prefix 深度、扇出、近期性、段类型、内存和物化成本；
- `prefetch_policy=none|oracle|file|service`：无预取、理论上限、文件预测和在线 GRU 服务；
- 完整的 delta、online、tree、family event、system parameter 输出。

test2 的核心边界是：同 LoRA 同 prefix 的 GPU full 才能直接降低当前 TTFT；跨 LoRA delta 的主要价值是压缩 Host/磁盘存储，只有提前 materialize 到 GPU 才可能影响下一请求 TTFT。

### 3.4 `lora-base-test2_100`：扩大请求规模而非改变 runtime

该目录保存 100 请求 OPUS-100 等并行前缀实验的结果、图和报告。它主要回答固定切分、自然句边界和 reuse-aware 在更长请求序列中的趋势。没有新增核心 C++ 逻辑，运行时仍来自 test2/test4 系列。

### 3.5 `lora-base-test3`：异步 delta 任务

test3 针对 test2 的主要瓶颈“delta 构建会阻塞前台请求”做了拆分：

1. `probe_delta_candidate` 只做质量探测；
2. `submit_variant_delta_async` 提交融合 CUDA job 并保存 job id；
3. 前台继续执行 suffix/decode；
4. `finish_variant_delta_async` 等待完成、做最终校验并降级为 Host delta；
5. 如果节点或 variant 已被淘汰则取消 job，不使用悬空序列。

因此 deferred 策略可以把一部分 delta 工作放在请求之间的空闲时间，但 test3 仍只有单个 pending job，统计字段也没有完全区分 submit 和 finish 等待时间。

### 3.6 `lora-base-test4`：统一 CPU/CUDA 执行策略

test4 增加 `delta_execution` 参数：

| 模式 | 实现 | 用途 |
|---|---|---|
| `cpu-sync` | 原始 CPU 逐层/逐 token 循环 | 正确性和慢速基线 |
| `cuda-sync` | 一次融合 CUDA 构建后立即等待 | 测量融合 kernel 的同步成本 |
| `cuda-overlap` | 提交一个或多个 CUDA job，先执行 suffix/decode，再统一 finish | 测量可重叠窗口 |

同时新增 `delta_submit_ms`、`delta_finish_wait_ms`、`delta_overlap_window_ms`、`delta_async_jobs`，并把在线同步路径和后台路径都接到 `build_delta_branch` 统一入口。test4 是当前最完整的通用 runtime，因此被 test6、test7 和 test8 复用。

### 3.7 `lora-base-test5`：四种调度的公平计时实验

test5 通过宏改名后 include test4：

```cpp
#define main llama_lora_base_test4_embedded_main
#include "../lora-base-test4/lora-base-test4.cpp"
#undef main
```

它只选择满足“相同 `common_prefix_text`、不同 LoRA”的 delta pair，重复执行四种模式，并把计时区域限定为 child-prefix 处理到首 token。`layer_pipeline_callback` 在每层输出完成时提交异步 delta，从而比较 layer-wise 与 all-layer CUDA 的差异。

test5 的贡献是实验边界和统计公平性，不是新的缓存系统。它不能替代 test4 的在线 prefix tree、预测预取或 family 淘汰。

### 3.8 `lora-base-test6`：真实数据集矩阵

test6 增加 Python runner 和 analyzer，把同一 runtime 放到六类 workload：MSC、Taskmaster、LMSYS、ShareGPT52K 连续增长前缀，以及 OPUS-100、XSum 并行共享前缀。矩阵比较 full-prefill、legacy exact、GPU-only、Host full、tiered、oracle chunk 和 disk delta store，并输出 CSV、热图、每数据集报告和总报告。

它解决的是“单个小样本难以比较策略”的问题，但 oracle 仍然是理论上限，不能当作真实预测器结果。

### 3.9 `lora-base-test7`：100 请求和前缀切分算法

test7 在 test6 的基础上：

- 默认使用 100 请求和更大的 `n_ctx`/cache budget；
- 对 Fixed 64/128、Fixed 192/384、Sentence、Keyword、Reuse-aware 做在线比较；
- 加入 Adaptive reuse v2：根据历史复用、未来节点数和预取预算调整边界；
- 加入 LoRA-focus filter v3 的消融；
- 增加 `diagnose_results.py`，区分“没有命中”与“命中了但 materialize/管理开销过大”；
- 对失败 cell、非正 TTFT 和输出行数做校验。

test7 的新增代码主要在 Python 实验编排和分析层，C++ 目标仍直接编译 test4 runtime。

### 3.10 `lora-base-test8`：注释和综合入口

test8 使用 test4 的独立副本，默认输出目录改为 `examples/lora-base-test8/output`，并在关键函数前加入中文说明：参数解析、token 精确校验、delta probe/build/finalize、缓存容量、chunk path、三级恢复、预取、后台窗口、结果写出和 main 生命周期。

它的目的不是再发明一个 test8 算法，而是让前面版本的最终可运行能力集中在一个易读文件中，便于你做本地实验、逐函数调试和向他人解释代码。

## 4. 综合架构

```text
workload JSONL
    |
    v
tokenize_request
    |  精确校验 common_prefix_tokens 是 prompt 的前缀
    v
ensure_chunk_path
    |  shared_system/context 按固定 token 步长建立累计前缀节点
    v
前台命中/构建
    |-- 同 LoRA gpu_full  -> seq_cp -> 跳过已命中 prefill
    |-- host_full          -> 反序列化到 GPU
    |-- host_delta         -> anchor + delta materialize
    `-- 无可用 variant     -> 正常 prefill 并加入缓存
    |
    v
suffix eval + decode -> 记录 TTFT/吞吐
    |
    +--> prediction (oracle/file/service)
    |       `--> family 保护和下一请求 prefetch
    |
    `--> delta queue
            `--> probe -> build/submit -> validate -> Host delta/disk
```

## 5. 一次请求的具体例子

设请求 prompt 为：

```text
S = shared system instructions
C = user/session context
T = task instruction
prompt = S + C + T
```

假设 tokenizer 得到 `S+C` 共 320 token，系统参数为 `system_chunk_tokens=64`、`context_chunk_tokens=128`，则可能建立：

```text
Root -> [0:64] -> [0:192] -> [0:320]
```

如果下一个请求使用同一个 LoRA，并且命中 `[0:192]` 的 `gpu_full` variant：

1. 复制 192 token 的 KV 到 request sequence；
2. 只对 token 192~320 的剩余 prefix 和 `T` 做 eval；
3. decode 第一个 token 时得到较低 TTFT。

如果下一个请求使用另一个 LoRA：

- 不能直接复制上面的 dense KV；
- 如果 anchor 和 child 的完整 KV 都存在，先执行 `probe`；
- 通过质量门槛后构建 `delta_q8 + scale`；
- 将 child 降级到 `host_delta`；
- 只有预取在请求到达前完成 materialize，才可能减少下一请求 TTFT。

delta 的近似形式是：

```text
KV_child ≈ KV_anchor + dequantize(delta_q8)
scale[t]  = max(abs(delta[t, :])) / 127
q8[t,j]   = clip(round(delta[t,j] / scale[t]), -127, 127)
```

因此 delta 的直接收益是节省 Host/磁盘空间；重建误差由 cosine/L2 和抽样 validation 记录。

## 6. 后续版本到底优化了什么

| 原问题 | 解决版本 | 新增代码/机制 | 直接效果 | 不能过度解读的地方 |
|---|---|---|---|---|
| 静态树难以复现实验 | test2 | JSON/JSONL loader、统一 options、结果 writer | 可批量运行和聚合 | 仍依赖 workload 构造质量 |
| 字符前缀可能与 token 前缀不一致 | test2 | `tokenize_request` 精确比较 token 序列 | 避免错误 KV 复用 | 离线估算 token 仍不是 tokenizer 真值 |
| 只能保存整段 prefix | test2 | chunked Prefix Tree、segment range | 支持部分 prefix 命中 | 节点越多会增加管理和淘汰开销 |
| 跨 LoRA KV 无法直接共享 | test2 | anchor + Q8 delta、probe、materialize | 降低 Host/磁盘存储 | delta 本身不会自动降低当前 TTFT |
| delta 构建阻塞请求 | test3 | async submit/finish/cancel | 可与 suffix/decode 重叠 | 不是独立后台线程，仍受同一 context 约束 |
| CPU delta 太慢且策略混杂 | test4 | `delta_execution` 统一 CPU/CUDA 路径 | 可公平比较同步和重叠 | cuda-overlap 仍需等待 finish 才能落盘 |
| GPU 容量不足时盲目删除 | test2-test4 | family 评分、降级、叶子优先淘汰 | 保护高价值 anchor 和预测 variant | 权重需要按 workload 校准，量纲可能失衡 |
| 预测结果不能落到 KV | test2 | oracle/file/service + prefetch | 在到达前准备目标 KV | oracle 不是可部署预测准确率 |
| 单数据集结论不稳定 | test6-test7 | 六数据集矩阵、100 请求、bootstrap/诊断 | 区分结构收益与管理开销 | 长上下文可能被 materialize 成本主导 |
| 代码难以整体阅读 | test8 | 综合副本、中文注释、独立 CMake target | 便于调试和讲解 | 没有新增生产级并发功能 |

## 7. 建议的本地运行顺序

先构建 test8：

```powershell
cmake --build build --config Release --target llama-lora-base-test8 --parallel 2
```

再用小请求数验证输入和输出路径（模型、LoRA 配置和 workload 路径按本机修改）：

```powershell
build/bin/Release/llama-lora-base-test8.exe `
  --workload-dir examples/lora-base-datasets/output/real_30/opus100_parallel `
  --output-dir examples/lora-base-test8/output/smoke `
  --max-online-requests 5 `
  --max-delta-pairs 4 `
  --system-v2 1 `
  --delta-execution cuda-overlap
```

常用对照：

- `--system-v2 0`：legacy exact-prefix；
- `--system-v2 1 --cross-lora-policy off`：只测同 LoRA prefix 和三级树；
- `--cross-lora-policy sync`：请求路径构建 delta；
- `--cross-lora-policy deferred --delta-execution cuda-overlap`：请求后/空闲窗口压缩；
- `--prefetch-policy oracle`：测预测理论上限；
- `--delta-store-policy build|load|auto`：测试磁盘 delta 生命周期。

输出重点：

| 文件 | 解释 |
|---|---|
| `delta_prefix_probe.csv` | pair 级 KV cosine/L2、delta 大小和构建时间。 |
| `delta_prefix_layers.csv` | 每层 K/V 的相似度。 |
| `online_request_results.csv` | baseline/online 每请求 TTFT、命中、预取、delta 和缓存指标。 |
| `online_prefix_tree.csv` | 最终节点、variant 驻留状态和 prefix 深度。 |
| `family_cache_events.csv` | 降级/淘汰动作、原因、收益、成本和分数。 |
| `system_parameters.csv` | 本轮完整配置，便于复现实验。 |

## 8. 当前实现边界

1. 只支持从 prompt 开头开始的 prefix 复用，不支持任意中间 token。
2. 不同 LoRA 即使文本相同，也不能直接共享 dense KV；必须走目标 LoRA 的 variant 或 anchor + delta。
3. 预测预取只有在请求到达前把目标 KV 准备到 GPU 才可能降低 TTFT。
4. `cuda-overlap` 是 API 级异步提交和延后等待，不等于已经实现独立后台线程、完全并发调度或单一融合推理 kernel。
5. Host full、Host delta、GPU full 是运行时状态模型；当前仍不是一个完全独立的 GPU compact-delta 物理池。
6. 物理 GGUF adapter 主要用于触发 LoRA 切换和 KV 路径，不代表它们已针对每个逻辑数据集训练。
7. family 分数是缓存管理启发式，不能直接当作“最佳切分点评分”；前缀切分算法和缓存淘汰应分开评估。

因此，test8 应描述为“可运行的多 LoRA Prefix-KV 策略实验原型”。它适合做消融、性能测量和代码学习，不应直接宣称已经完成生产级异步缓存系统或端侧部署。
